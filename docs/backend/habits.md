# Habits API contract

## Scope and ownership

Habits are durable user-owned definitions. Habit logs are separate, append-by-date progress records and remain available when a habit is archived. The frontend currently uses MSW for the endpoints below; this document describes the future backend contract only.

## Models

### `Habit`

```json
{
  "id": "habit-1",
  "name": "Gym",
  "description": "Strength training",
  "schedule": {
    "type": "weekdays",
    "weekdays": [1, 3, 5]
  },
  "targetCount": 1,
  "unit": "session",
  "state": "active",
  "createdAt": "2026-09-22T09:00:00.000Z",
  "updatedAt": "2026-09-25T16:30:00.000Z"
}
```

Required fields are `id`, `name`, `schedule`, `state`, `createdAt`, and `updatedAt`. `description`, `targetCount`, and `unit` are omitted when absent. Names are trimmed and limited to 100 characters; descriptions are limited to 2,000 characters. A target is a positive integer. A unit is optional display text.

`state` is `active` or `archived`. Archiving changes only the definition state and `updatedAt`; it never deletes or rewrites logs. Archived habits remain readable, including their history, but do not appear in Today and reject new log writes.

### `HabitSchedule`

`schedule` is a discriminated value stored on the habit:

```json
{ "type": "daily" }
```

```json
{ "type": "weekdays", "weekdays": [1, 3, 5] }
```

```json
{ "type": "weekly-target" }
```

Weekdays use ISO numbering: Monday is `1`, Sunday is `7`. A `weekdays` schedule requires at least one distinct weekday. Daily and weekday habits may have an optional per-day `targetCount`, such as 8 glasses or 30 minutes. A `weekly-target` schedule requires `targetCount`, interpreted as the amount to accumulate in one calendar week; progress may be logged on any day. Weekly periods run Monday through Sunday in the user's effective IANA timezone.

### `HabitLog`

Logs have a separate lifecycle and uniqueness boundary from habits:

```json
{
  "habitId": "habit-1",
  "date": "2026-09-25",
  "progress": 1,
  "completed": true,
  "timeZone": "America/New_York",
  "createdAt": "2026-09-26T00:15:00.000Z",
  "updatedAt": "2026-09-26T00:15:00.000Z"
}
```

The unique key is `(userId, habitId, date)`. `date` is the user's local calendar date in `YYYY-MM-DD` form, not a UTC date or timestamp. `progress` is a non-negative integer containing the absolute count for that habit on that date. For an untargeted habit, progress is `0` or `1`. `completed` is derived by the server: for daily/weekday habits, progress must meet the per-day target (or be greater than zero when untargeted); for weekly targets, it becomes true on the date that the week's cumulative progress reaches the target. `timeZone` is the IANA timezone used to interpret the local date and schedule. `createdAt` and `updatedAt` are UTC ISO-8601 instants generated by the server.

## Local dates, timestamps, and timezone changes

- The client derives the date from the user's configured IANA timezone and sends that local date explicitly. Until profile timezone settings exist, the frontend uses the device's current timezone.
- The server validates the IANA timezone and date, but does not derive a habit date by truncating a UTC timestamp. UTC is used for audit timestamps only.
- The log's local date is stable history. Changing the user's timezone does not shift, merge, or rewrite existing log dates. The stored timezone records the interpretation used for the latest accepted write to that date key.
- After a timezone change, new activity uses the new effective timezone. Since the idempotency key remains `(userId, habitId, date)`, writes to the same date upsert the same record rather than creating a duplicate.
- Scheduled-day membership and Monday-to-Sunday week boundaries are evaluated in the effective timezone. DST transitions do not change the `YYYY-MM-DD` identity of a log.

## Endpoints

### `GET /api/habits`

Lists the authenticated user's habits. Optional `state=active|archived` filters by state. Return definitions sorted by state, then stable creation time and ID.

```json
[
  {
    "id": "habit-1",
    "name": "Gym",
    "schedule": { "type": "weekdays", "weekdays": [1, 3, 5] },
    "state": "active",
    "createdAt": "2026-09-22T09:00:00.000Z",
    "updatedAt": "2026-09-25T16:30:00.000Z"
  }
]
```

### `POST /api/habits`

Creates an active habit. The server assigns its ID and UTC timestamps. A weekly-target schedule requires a positive `targetCount`.

```json
{
  "name": "Workout",
  "schedule": { "type": "weekly-target" },
  "targetCount": 3,
  "unit": "sessions"
}
```

Return `201 Created` and the full `Habit`.

### `PATCH /api/habits/:habitId`

Updates a non-empty subset of `name`, `description`, `schedule`, `targetCount`, and `unit`. Validate the merged definition, including the weekly-target requirement, and set `updatedAt` to the current UTC instant. Return the full updated `Habit`.

### `POST /api/habits/:habitId/archive`

Archives an owned habit. This operation is idempotent. Return the archived `Habit`; preserve every log. Re-archiving does not change history.

### `GET /api/habits/:habitId/logs?from=YYYY-MM-DD&to=YYYY-MM-DD`

Returns that habit's logs, inclusive of both date bounds and sorted by local date ascending. Omit either bound to leave that side open. Archived habit history remains readable.

### `GET /api/habit-logs?from=YYYY-MM-DD&to=YYYY-MM-DD`

Returns date-bounded logs for the user's habits. This aggregate read supports the weekly view without one request per habit. It follows the same inclusive bounds and ordering.

### `PUT /api/habits/:habitId/logs/:date`

Creates or replaces the progress record for one habit and local date. The request expresses an absolute daily value, not an increment operation, so retrying a request cannot double-count progress.

```json
{
  "progress": 5,
  "timeZone": "America/New_York"
}
```

The server derives `completed` from the current habit definition and all same-week logs when applicable, and generates UTC timestamps. A repeated request with the same progress and timezone returns the same logical log without adding another record. If values differ, update the existing row and its `updatedAt`. Use a transaction or equivalent atomic upsert on `(userId, habitId, date)` so concurrent retries remain idempotent.

## Today projection and streaks

Today includes active daily habits, weekday habits scheduled on the user's current local weekday, and weekly-target habits whose current local week has not yet reached its target. Completed daily habits remain visible for the day; a completed weekly target no longer needs today's attention. Unscheduled weekdays are omitted from Today and must not be represented as missed completions in history.

The backend is authoritative for streak calculation because it has complete history and the effective timezone. The frontend may display a local preview, but should not persist streak values. For daily and weekday schedules, count consecutive scheduled dates with completed logs; skip unscheduled dates. An incomplete current local date remains pending until that date ends. For weekly-target schedules, count consecutive Monday-to-Sunday weeks that met the aggregate target; a still-open current week does not break the previous streak, while a closed week below target does. The Today dashboard should return its streak projection or expose equivalent streak metadata on the habit read model.

## Errors

Errors use `{ "code": "...", "message": "..." }`.

| Status | Code                 | Condition                                                                               |
| ------ | -------------------- | --------------------------------------------------------------------------------------- |
| `400`  | `INVALID_LOCAL_DATE` | Invalid or impossible date, unsupported timezone, or invalid date/timezone combination. |
| `401`  | `UNAUTHENTICATED`    | No valid session.                                                                       |
| `404`  | `HABIT_NOT_FOUND`    | Missing or inaccessible habit.                                                          |
| `409`  | `HABIT_ARCHIVED`     | Attempt to write a new log to an archived habit.                                        |
| `422`  | `INVALID_HABIT`      | Invalid name, schedule, target, unit, or update.                                        |
| `422`  | `INVALID_HABIT_LOG`  | Invalid date, timezone, or progress value.                                              |

Use `5xx` for unexpected persistence failures. Validate ownership on every definition and log request; do not reveal whether an inaccessible ID belongs to another user.
