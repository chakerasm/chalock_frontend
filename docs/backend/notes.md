# Notes API contract

## Scope and entity

Notes are lightweight personal captures. They contain plain text only; folders, relations, rich-text blocks, and collaboration are out of scope. The frontend uses MSW for these endpoints; no backend implementation is included here.

```json
{
  "id": "note-1",
  "title": "For Monday",
  "content": "Ask Priya about the conference room before booking.",
  "pinned": true,
  "createdAt": "2026-09-20T09:00:00.000Z",
  "updatedAt": "2026-09-25T16:30:00.000Z"
}
```

Required fields are `id`, `content`, `pinned`, `createdAt`, and `updatedAt`. `title` is optional and omitted when absent. Title is trimmed and limited to 120 characters. Content is plain UTF-8 text, trimmed only for validation/storage boundary policy, and limited to 20,000 characters. Empty content is rejected. Instants are UTC ISO-8601 timestamps generated by the server.

## Endpoints

### `GET /api/notes`

Lists notes owned by the authenticated user. Optional `search` performs case-insensitive literal substring matching across title and content. Search does not interpret query syntax or Markdown. Return notes ordered pinned first, then `updatedAt` descending, then stable ID ascending.

### `GET /api/notes/:noteId`

Returns one owned note. Use `404 NOTE_NOT_FOUND` for missing or inaccessible notes.

### `POST /api/notes`

Creates a note with `{ "content": "...", "title": "..." }`; `title` may be omitted. The server sets `id`, `pinned: false`, `createdAt`, and `updatedAt`. Return `201 Created` and the full Note.

### `PATCH /api/notes/:noteId`

Accepts a non-empty subset of `title`, `content`, and `pinned`. `title: null` clears the optional title. Set `updatedAt` on each accepted write. Reject blank content, over-limit values, and empty patch bodies. Return the full updated Note.

### `DELETE /api/notes/:noteId`

Deletes an owned note and returns `204 No Content`. This is a user-confirmed hard delete. If future retention requirements require soft deletion, preserve the same client behavior.

## Autosave, optimistic updates, and concurrency

- The client debounces content/title edits for about 650 ms after the last change and sends one PATCH containing the current draft. Pin changes can be sent immediately. Create remains an explicit capture action.
- Avoid one toast per keystroke. The editor presents a quiet saving/saved state and keeps the draft visible if saving fails, with a retry action.
- The current client updates its local editor draft immediately, then revalidates the Notes list after a successful write. If implementing optimistic query-cache updates, cancel in-flight note-list requests, snapshot the previous cache value, update or reorder the item locally, and roll back that snapshot on error before invalidating/refetching.
- The server's `updatedAt` is the last accepted-write timestamp, not a concurrency token. Before multi-device or collaborative editing, add a monotonically changing revision or ETag and require `If-Match` (or an equivalent revision) on PATCH. Return `409 NOTE_EDIT_CONFLICT` for stale writes and let the client offer reload/overwrite; last-write-wins is acceptable only for the initial single-user version.
- A slow autosave response must not replace a newer local draft. Clients should sequence writes per note or ignore responses older than the current draft revision.

## Errors

Errors use `{ "code": "...", "message": "..." }`.

| Status | Code                 | Condition                                            |
| ------ | -------------------- | ---------------------------------------------------- |
| `401`  | `UNAUTHENTICATED`    | No valid session.                                    |
| `404`  | `NOTE_NOT_FOUND`     | Missing or inaccessible note.                        |
| `409`  | `NOTE_EDIT_CONFLICT` | Stale revision, when revision checks are introduced. |
| `422`  | `INVALID_NOTE`       | Empty/over-limit title or content, or invalid patch. |

Use `5xx` for unexpected persistence failures. Do not reveal whether inaccessible IDs belong to another user.
